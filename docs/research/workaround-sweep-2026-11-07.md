## Notes on the judgement calls

- **Row 9 (seedListener retry).** Verdict: Workaround, lean towards "hides a slow `listAgents()`". `listAgents()` is `fetchAgents().entries` (`runner-backend.mjs:523`), and `seedListener` wraps it in `bounded()` (8 s). A first fetch that fails means the runner did not answer in 8 s. With R1/R2 merged that should not happen on a healthy runner, so the retry only matters when the runner is hung or still booting. In that case a retry loop makes the pill clear without Ctrl+R but gives no signal that the runner was slow. Suggest: keep the retry only if it also logs a `seed-slow` metric (attempt count plus ms), so a second attempt is visible.
- **Row 8 vs row 9.** `seedRoster` already retries for the shared stream; `seedListener` adds a second, per-listener loop. The second one is only needed if a listener subscribes while the shared seed is mid-failure. S2 resolves that by cancelling listener retries when `seedRoster` lands (diff: `seedTimers.clear()` in `seedRoster`).
- **Row 1** is not in the repo. The 32 value is a per-machine env var. Memory cost is the reason the default is 16 (`runner/runner.mjs:43` comment, ~0.4 GB per claude).
- **Rows 10/11** are the same lever (cap) at three stages: 6, then 16 with a queue, then per-turn caps. Only the last one removes the cause.
