# Security Policy

## Threat Model

VibeSquad is a **local-first** tool. Its default attack surface is minimal:

- **Loopback only by default.** The web server binds to `127.0.0.1` (default port 4180, `VIBESQUAD_PORT`; `server/serve.mjs:482`, `server/auth.mjs:86`). No network traffic is accepted from other machines unless you explicitly enable LAN or meshnet access.
- **What is trusted on loopback:** only callers that hold the per-install **local token**. The server creates `~/.vibesquad/local-token` (32 random bytes, hex) on first use, mode 0600 (`server/local-token.mjs:166-175`), with `~/.vibesquad` ACL'd to the current Windows user (`server/auth.mjs:156-169`, `icacls` at `:149`). Owner access needs either the `x-vibesquad-token` header (the `vs` CLI, the desktop proxy; `server/local-token.mjs:11`) or the `vs_local` session cookie (HttpOnly, SameSite=Strict, no Max-Age; `server/auth.mjs:737`) that the launcher-only bootstrap `GET /__vibesquad/local-login?t=<nonce>` sets. `t` is a single-use 128-bit nonce that expires after ~60 s and is held in server memory (`server/auth.mjs:696-703`). While it sits on the browser's command line, anyone who reads it and redeems it first within those ~60 s gets the session (first redeemer wins). After that it's worthless. The master token is never accepted there, so it never appears on a browser command line or in history. The server's `--open` launcher mints the nonce in-process. `vs open` (and a second `--open` while the server runs) gets one from `POST /__vibesquad/local-login/nonce`, which needs the header token (`server/auth.mjs:751`).
- **Loopback without the token is read-only:** GET/HEAD must pass the Host / Origin / Fetch-Metadata loopback check (`server/auth.mjs:557-568`). Every non-GET/HEAD method gets 403 `{readOnly: true}`, and so do GETs that hand out file contents or secrets or spawn processes: local-image, VAPID key creation, forced provider refresh, schedules, terminals, git diffs, and workspace quick-open/find (`server/vibesquad-api.mjs:373-391`, `:1645-1646`). The web UI shows a one-line read-only banner in that state.
- **Desktop app:** its loopback proxy (default port 4189) requires a per-launch `vs_desktop` cookie that the app sets in its own window at startup (`/__desktop/boot`). It forwards the local token only to a local server (an exact `localhost`/`127.0.0.1`/`[::1]` host), and only after that listener proves it already holds the token: a fresh nonce goes to `GET /__vibesquad/local-proof` and the HMAC-SHA256 answer (keyed with the token, bound to the port) is checked in constant time before the header is written, on the same hand-dialed TCP connection that then carries the request (`src-tauri/src/local_proof.rs:53`, `:227-250`, `:255`; HTTP `main.rs:2264-2302` via `:2458`, WebSocket `:1866`). A listener that fails the proof gets no retry and no other candidate: the window sees a plain 502 and the token was not sent (`:2310`, `:2496`; WebSocket side closes, `:1877`). The proxy states `Origin: <scheme>://<host>` on every upstream request so the server's same-origin check for cookie writes does not depend on the webview (`:2450`, `:2290`, `:2478`), and it never forwards `vs_desktop`/`vs_local` upstream (`:527`, `:689`, `:721`, `:2748-2805`). In `--headless-proxy` test mode the key check is off (`:2916`), so the proxy attaches no local token either.
- **UNC paths:** client-supplied paths (`local-image`, `workspace-package-scripts`, `attach`) that start with `\\` or `//` are refused before any filesystem call, so a request can't make Windows contact another host and send NTLM credentials. The allowlist is checked on the resolved path before `stat`/`realpath` (`server/vibesquad-api.mjs:610-620`), then again on the real path after `realpath` (`:650`, `:784-785`).
- **Agent identity (X1a, X1c).** The runner is the only agent backend (`server/backend/index.mjs:1-13`) and listens on `127.0.0.1` (`runner/server.mjs:323`). It mints one secret per agent, held in memory only and exported to that agent's child as `VS_AGENT_TOKEN`; an inherited one is dropped first (`runner/runner.mjs:28-47`, X1a `b2d8c15`, merged `6aaa6c3`). `GET /verify-agent` answers who a caller is from that memory (`runner/server.mjs:143`). The VS server then sorts every `/__vibesquad` caller into owner, agent or unknown (`server/auth.mjs:615-690`, X1c `b301dd0`, merged `8bad474`): a request that names an agent is never the owner, a wrong or missing agent token is a 403, and a runner that can't answer is a 503, never a fallback to owner. Agents may write only to a fixed allowlist of routes; every other write is owner-only (`server/vibesquad-api.mjs:305-318`, `:1645-1647`), and handlers re-check the agent's role and lane. Agents cannot set protected labels such as role, lane, team (`runner/runner.mjs:48-60`). Limit: same-user memory reads are not blocked (see Known Scope Limits).
- **What requires explicit opt-in (LAN/meshnet access):** turn it on with `--lan`, `VIBESQUAD_LAN=1`, or the Settings LAN toggle (`server/serve.mjs:58-65`); `VIBESQUAD_LAN_IP` / `VIBESQUAD_MESHNET_HOST` pick the addresses. When enabled, the server generates a local root CA with strict X.509 `nameConstraints` (`server/auth.mjs:223-238`; only `localhost`, `127.0.0.1/32`, the configured host, and the exact `/32` LAN / Meshnet IPs; no ranges), and all remote access requires a device token obtained by scanning a QR code from the local UI (single-use, 5-minute TTL; `server/auth.mjs:14`, `:796-835`, `:1061`). Failed pairing attempts are rate-limited per IP (`server/auth.mjs:1048`). The CA's SHA-256 fingerprint is shown in the pairing flow and put in pairing links so the Android app can pin the CA (`server/auth.mjs:345`, `:984-1006`); compare it with the one on your PC.
- **Token pairing:** each device receives a per-device cookie (`vs_device`) after completing the pairing flow. The cookie is a random bearer token: the server stores only its SHA-256 hash and compares it in constant time; it is `HttpOnly; Secure; SameSite=Strict` with a one-year lifetime (`server/auth.mjs:1064-1074`, `:514-523`). It is **not** bound to the device or to the CA fingerprint, so a cookie copied off a device works from any client that trusts the local CA until it is revoked (`vs devices revoke <id|--all>`, or the Pair a device dialog; `server/auth.mjs:774-786`, `:1119`). A revoke made from another process (E4a `9da81fb`) is picked up within about a second and cuts that device's open streams (`server/auth.mjs:354-357`, `:378-422`). **Cookie writes need a same-origin proof (X1-E4b L4):** every non-GET/HEAD request (OPTIONS included) that the `vs_device` cookie would authenticate must also carry an `Origin` equal to the listener's own `scheme://Host`, or no `Origin` with `Sec-Fetch-Site` absent, `none` or `same-origin`; anything else is refused with 403 before the token is even looked up (`server/auth.mjs` `cookieWriteRefusal`, called from `authenticate`, so both listeners share the one chokepoint). A request with neither header is allowed on purpose: every browser and the Android WebView send `Origin` on every POST, so that shape only comes from non-browser clients (the desktop proxy forwarding to a remote host strips `Origin`, curl-style tooling). Relayed requests authenticate by channel identity and never reach this check; `x-vibesquad-token` and agent-header callers are not cookie auth and are covered by the loopback Host/Origin check instead, which since `4750a14` also requires the listener's own origin (or the Tauri shell origin) for the `vs_local` loopback cookie, so a page on another loopback port is refused even in browsers that send no `Sec-Fetch-Site`.
- **Outbound E2EE relay: wired in, off by default, no hosted relay.** The relay (X25519 key exchange, AEAD, per-dispatch revoke re-check; E5 core `fbe014c`, hardening `ba6bb08`, wiring `4996b66`) runs inside the live server, but it only starts when `~/.vibesquad/settings.json` has a `relay.endpoint` that is a `wss://` URL (`server/user-settings.mjs:201-205`, `server/relay-wiring.mjs:218-219`, `server/serve.mjs:535-539`). That file is edited by hand: no HTTP request can set it (`server/user-settings.mjs:193-195`). No hosted relay server ships, so nothing in the app turns this on for you. **Relay pairing links (E5 §7 item 8):** once a relay is running, the Pair a Device dialog also shows a relay link and QR for the same one-time code (`server/auth.mjs:1119-1130` `relayPairingFor`, `:1332-1335`; card `src/PairDeviceModal.tsx:471`). The link is `vibesquad://pair#hostId=&pub=&relay=&code=` (`server/relay-link.mjs:35-50`): everything is in the fragment, so no browser or relay ever sends the code to a server log, and `relay=` is the public endpoint only (origin + path, `server/relay-link.mjs:17-20`), never userinfo or query of the dial URL. The offer exists only while the wiring reports `running` on a `wss://` endpoint and comes from the same read-only status registration the Host pill uses (`server/vibesquad-api.mjs:457`); no HTTP route can set relay settings. On the phone (`src/remoteRelayConnect.ts`), a link first has to be self-certifying (`:83-84`), then the **stored key for that relay id always wins**: a different key for a known host is `RelayPinMismatchError`, shown in plain words, nothing written (`:92`, `src/remoteSession.ts:468`); the session is opened with the stored key (`:127`) and the device token is only ever sent after that pinned handshake. A known host's relay endpoint is never moved by a link on its own (X1 wire L2): the user gets a plain yes/no, Cancel keeps the current relay (`:95`, `src/RemotePairScreen.tsx:166`; `src/remoteSession.ts:469` only moves it with `repoint`). Nothing is persisted before the handshake and the PC's redeem succeeded through the endpoint actually used (`:182`). One PC keeps one `hosts[]` entry: the E4a host id AND CA fingerprint are learned over the authenticated channel, cross-checked against the pin, and folded into a LAN entry only when both match (E4a's `samePc` rule; `src/remoteRelayConnect.ts:196-201`, `src/remoteSession.ts:497-518`). The public id alone never folds, a LAN-proven entry never changes identity over the relay, and the pairing order does not matter (review R1 M2). A LAN re-pair at a known address by a different PC (other id or other CA) drops the old PC's relay pin and token (`src/remoteSession.ts:314`, `:333`; R1 M1), and a LAN entry is never matched by its id for a pin (`src/remoteSession.ts:408`). A device-minted (pending) code never replaces a working relay token: the ticket is parked beside it and promoted only once it authenticates (`src/remoteRelayConnect.ts:149-170`; R1 L3). A relay-only pairing can be forgotten by its relay id (`src/remoteSession.ts:360`, `src/RemotePairScreen.tsx:428`; R1 L2), and the Android boot diagnostic drops any URL fragment before logging it (`src/diagOverlay.ts:49`; R1 L1). Residual: the CA fingerprint a relay host claims is not TLS-proven (the server hands it to unpaired LAN callers too), so the fold binding is id+fingerprint strength, the same as E4a's `samePc`, not stronger. The relay session UI itself is not built yet (E5 §7 item 6): the phone pairs, stores the pin + token and reports; the LAN/Meshnet path still opens the PC's own UI. A relayed request is never treated as local: it gets no loopback trust, local token, local login or local proof (`server/auth.mjs:614`, `:654`, `:669`, `:709`, `:722`), and it runs through the same guarded handler as LAN requests (`server/serve.mjs:539`). Revoking a device, including from the `vs` CLI or another process, closes its relay sessions (`server/relay-wiring.mjs:98`, `:183`). `vs host-key rotate` replaces the host relay key and revokes every paired device (LAN ones too) unless you pass `--keep-devices` (`cli/vs.mjs:2188-2194`). Until you have set up a relay yourself, treat this as inactive.
- **CLI and MCP prove the loopback listener first (`1b6b2e6`).** Before the `vs` CLI or the MCP tools send the local token, they challenge the listener over a single socket and check an HMAC-SHA256 answer keyed with that token, so a rogue process on the port can't collect it (`server/local-token.mjs:51-66`, `:148`; `server/auth.mjs:1455-1457`).
- **Web Push:** push notifications are sent to endpoints the user subscribed to from their own browser. No message content other than agent status events is sent.
- **No outbound telemetry.** VibeSquad makes no calls to external analytics or telemetry services.

## Known Scope Limits

- **Multi-user PCs:** the local token stops other Windows users and other local apps from changing VibeSquad, but they can still **read** through the loopback API (teams, logs, settings, inbox). Anyone who can read your `~/.vibesquad` (an administrator, or malware running as you) has full access. Browsers send cookies to every port on `127.0.0.1`/`localhost`, so a hostile server another user runs on a loopback port could capture your `vs_local` cookie if you browse to it. Delete `~/.vibesquad/local-token` and restart the server to rotate it.
- **Accepted limit (same OS user):** agents run as the same OS user as the owner. An agent that deliberately reads `~/.vibesquad/local-token` is therefore treated as the owner. This is accepted for 0.3. The real fix (a separate OS account or sandbox per agent) is post-0.3.
- Rotating the token needs a server restart, and clients re-read the file on their next request.

- VibeSquad began on top of the Paseo daemon; it no longer uses it. Agents run through VibeSquad's own runner.
- Agent prompts and transcripts are handled by the AI provider (Anthropic, Google) under their own terms. VibeSquad never sends transcript content to any server.
- `teams.json` contains project paths and team names. It is gitignored; keep it out of public repositories.

## Reporting a Vulnerability

Please report security vulnerabilities **privately** using [GitHub Security Advisories](https://github.com/your-org/vibesquad/security/advisories/new).

Do **not** open a public issue for security vulnerabilities. We will acknowledge reports within 5 business days and aim to release a fix within 90 days depending on severity.

When reporting, please include:
- A description of the vulnerability and its impact
- Steps to reproduce or a proof-of-concept
- The version or commit hash you tested against
- Whether you believe this is exploitable remotely or only locally
