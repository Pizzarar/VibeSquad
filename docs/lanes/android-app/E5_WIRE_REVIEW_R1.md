## (b) Threat Hunt Results

1. **Can a relay principal reach a local-only route or `/local-proof`, `/local-login`, `/local-login/nonce`?**
   - **No.** `/__vibesquad/local-login` and `/__vibesquad/local-login/nonce` are blocked at the tunnel allowlist (`RELAY_DENIED_PREFIXES` in `server/relay-tunnel.mjs:271`, prefix-matched on the canonical lowercase path before dispatch) AND gated by `isLocalBrowserSafe(req)` + `hasLocalTokenHeader(req)` inside `server/auth.mjs:845,861`. `/__vibesquad/local-proof` reaches `handleLocalProof` (`server/auth.mjs:1464-1474`), where `if (!isLocalBrowserSafe(req))` immediately returns `403 { error: "loopback only" }` because `isRelayRequest(req)` forces `isLocalBrowserSafe` to `false`.
2. **Can headers be smuggled past the 5-header allowlist?**
   - **No.** `pickHeaders` (`server/relay-tunnel.mjs:315-322`) creates a fresh object copying only keys in `FORWARD_HEADERS` (`content-type`, `accept`, `if-none-match`, `if-modified-since`, `range`) whose values are strings, and `createSyntheticRequest` (`:349`) overwrites `host: "relay.invalid"`. Agent headers (`x-vs-agent-id`, `x-vs-agent-token`), `cookie`, `x-vibesquad-token`, `x-vs-token`, `origin`, and `sec-fetch-site` can never be injected by a relay client.
3. **Can a revoke race leave a live stream open?**
   - **No, with one minor Low nuance on `createInProcessStreamBridge` request-body consumption (see Finding L1 below).** Every in-process and out-of-process revoke path triggers `dropDeviceSockets(id)` -> `onDeviceDropped` -> `host.revoke(id)` -> `closeSession(cid)`, which synchronously calls `w.close()` on every open `s.ws` stream (`server/relay-tunnel.mjs:586-590`) and marks `s.dead = true` so in-flight `send()` calls drop (`:603`). In addition, `dispatch` re-checks `await isRevoked(s.deviceId)` on every post-auth frame (`:766`) and `runHttp` checks `if (s.dead) return;` after `await handleHttp(...)` (`:661`).
4. **Can pending-token polling act as an oracle?**
   - **No.** `pendingForToken(token)` (`server/auth.mjs:942-950`) hashes the caller's token with SHA-256 and compares against `pendingDevices` in constant time (`timingSafeEqual`). A pending token is a 256-bit `randomBytes(32).toString("base64url")` secret returned only to the client that redeemed the valid 1-time code (`:1329`). Guessing a random token has $2^{-256}$ probability, and every non-matching guess is NOT pending, so it stays counted in `s.redeems` (max 5 per session) and `authFails` (max 100/min host-wide, `:741-753`). Even a holder of a real pending token is bounded by the 1-frame pre-auth backpressure cap (`:832`) and the 30s `authTimeoutMs` timer (`:822`).
5. **Can key rotation leave the old key usable?**
   - **No.** `checkKeyFile()` (`server/relay-wiring.mjs:125-140`) detects any stamp change (or deletion, creating a fresh keypair), calls `adoptKey(next)` (`:113-123`) which builds a new `createRelayHost` with the new key and self-certifying `hostId`, calls `old.revokeAll()` (sending `{ t: "close", cid }` to all sessions on the old host) and `old.stop()` (closing the old relay WebSocket and clearing reconnect timers), and starts the new host.

## (c) Findings

### 1. [LOW] `createInProcessStreamBridge` does not drain `req`, so `req.on("close")` handlers that neglect `res.on("close")` wait until stream teardown (`server/relay-tunnel.mjs:343,434`)
- **Location:** `server/relay-tunnel.mjs:343-355`, `server/relay-tunnel.mjs:429-509`, `server/terminals-api.mjs:48-55`
- **Failure scenario:** `createSyntheticRequest` creates `const req = Readable.from([])`. In Node.js, `Readable.from([])` does not auto-consume or emit `"end"`/`"close"` until a consumer reads from it or `.destroy()` is called. When `createInProcessStreamBridge` finishes or is closed by the client/revoke (`finish(code)` at `server/relay-tunnel.mjs:437-449`), it calls `req.destroy()` and `res.destroy()`, which asynchronously emits `"close"` on both `req` and `res` — so cleanup works on normal close and revoke. However, if a streaming handler attaches cleanup only to `req.on("close", ...)` (as `server/terminals-api.mjs:55` does) and the response errors or terminates via a path that only destroys `res` without calling `finish()`, `req` never emits `"close"`. (Note: `server/runner-api.mjs:29-30` attaches to both `req.on("close")` and `res.on("close")`, and `finish()` in `createInProcessStreamBridge` destroys both `req` and `res`, so all current SSE routes clean up properly on revoke and client close.)
- **Suggested fix:** Either keep `finish()` as the single teardown path (already destroying both `req` and `res`) and add `res.on("close", () => finish(1000))` in `createInProcessStreamBridge` (`server/relay-tunnel.mjs:494`) so a handler calling `res.destroy()` directly also triggers `finish()` and destroys `req`.
